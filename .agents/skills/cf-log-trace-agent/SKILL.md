# SAP CAP Cloud Foundry Log & Trace Agent Skill

This skill documents the architecture, authentication mechanisms, synchronization workflows, and **authoritative Cloud Foundry Error Resolution Catalog** for the `cf-log-trace-agent` SAP CAP service.

---

## 🏗️ Architecture & Telemetry Schema

The `cf-log-trace-agent` service connects to SAP BTP Cloud Foundry APIs (`/v3/apps`, `/v3/audit_events`), transforms container telemetry into relational CDS models, and exposes an **autonomous AI remediation loop** via Model Context Protocol (MCP) and SAP Fiori Elements.

### Core Domain Entities (`db/schema.cds` under `shubh.incidents`):

1. **`Incidents` (Root Entity - `: cuid, managed`)**:
   - `applicationId`: Cloud Foundry Application GUID (`app.guid`) or audit event target identifier.
   - `correlatedRequestId`: Correlated request ID or audit event GUID (`event.guid`).
   - `targetSpace`: Cloud Foundry space GUID or space name (e.g., `dev`, `prod`).
   - `status`: Incident lifecycle status (`OPEN`, `INVESTIGATING`, `RESOLVED`, `CLOSED`).
   - `errorCategory`: Categorized taxonomy (`CF_APP_CRASH`, `CF_PROCESS_CRASH`, `CF_ROUTE_MUTATION`, `CF_RESOURCE_DELETED`, `CF_APP_RESTAGE`, `CF_APP_STATUS`, `CF_AUDIT_LOG`).
   - `rootCauseStatement`: Human- and AI-readable explanation of the detected failure.
   - `remediationAction`: Prescriptive, actionable remediation command sequence.
   - `impactedServices`, `traces`, `messages`: Compositions cascading with RFC 4122 v4 UUIDs generated by the CAP runtime (`cuid`).

2. **`ImpactedServices` (`: cuid`)**:
   - Linked to `Incidents` via `incident_ID`.
   - Records `serviceName` and `instanceId`.

3. **`TraceEvents` (`: cuid`)**:
   - Detailed event log containing `timestamp`, `component` (`APP`, `RTR`, `CELL`), `statusCode`, `logLevel`, and raw `message`.

4. **`Messages` (`: cuid, managed`)**:
   - Chronological audit notes, agent diagnostic logs, and operator collaboration comments.

## 🔑 Cloud Foundry Authentication Priority & Handling

The authentication helper `getCloudFoundryToken()` in `srv/incidents.ts` resolves credentials using the following hierarchy:

1. **Direct Bearer Token (`CF_BEARER_TOKEN`)**:
   - Highest priority. Fast and bypasses interactive password limits.
2. **User Password Grant (`CF_USERNAME` & `CF_PASSWORD`)**:
   - Authenticates against `CF_TOKEN_URL`.
   - *Security Guard:* If the SAP ID Service / IAS returns `PASSWORD_LOCKED`, the service logs an explicit alert and halts authentication to avoid account ban escalations.
3. **Client Credentials Grant (`CF_CLIENT_ID` & `CF_CLIENT_SECRET`)**:
   - Production recommendation for BTP service bindings and automated batch jobs.
4. **Local CF CLI Session Fallback (`cf oauth-token`)**:
   - Automatically reuses the active developer session from the local workstation.

## 🚨 Cloud Foundry Error Resolution Catalog & Playbooks

When analyzing incidents or generating `remediationAction` plans, consult the following authoritative diagnostic signatures and resolutions:

### 1. Application Lifecycle & Runtime Errors

#### A. Out of Memory (OOM) Crash (`Exit 137`)
- **Symptoms:** Container crashes shortly after peak traffic or startup. `status = 'INVESTIGATING'`.
- **Diagnostic Signature:**
  - `cf events <app>` displays `app.crash` with `exit_description: "out of memory"` or `exit_status: 137`.
  - `TraceEvents` shows `component: 'CELL'`, message indicates memory cgroup ceiling breached.
- **Root Cause:** Container memory usage exceeded allocated quota.
- **Resolution Steps:**
  1. Scale container memory quota immediately:
     ```bash
     cf scale <app_name> -m 1G
     ```
  2. If Node.js application, configure V8 maximum heap allocation in `manifest.yml`:
     ```yaml
     env:
       NODE_OPTIONS: "--max-old-space-size=800"
     ```
  3. Inspect memory leaks using heap profiles or audit recent large payload queries.
  4. Restage app to apply new resource limits: `cf restage <app_name>`.

#### B. Application Process Failure (`Exit 1` / `Exit 255`)
- **Symptoms:** App fails to start or crashes in a `CrashLoopBackOff`.
- **Diagnostic Signature:**
  - `cf logs <app> --recent` contains uncaught exception, missing module, or unhandled rejection.
  - `exit_status: 1` or `255`.
- **Root Cause:** Missing environment variables, missing service bindings, database connection refusal, or code exception.
- **Resolution Steps:**
  1. Capture recent standard error output:
     ```bash
     cf logs <app_name> --recent
     ```
  2. Verify environment bindings:
     ```bash
     cf env <app_name>
     ```
  3. If missing environment configuration, supply the variable:
     ```bash
     cf set-env <app_name> <KEY> <VALUE>
     ```
  4. Restart application:
     ```bash
     cf restart <app_name>
     ```

#### C. Graceful Termination Timeout (`Exit 143`)
- **Symptoms:** App instances take too long to shut down during rolling deployments or restarts.
- **Diagnostic Signature:** `exit_status: 143` after SIGTERM signal.
- **Root Cause:** Application failed to release network sockets or database connections within default 10-30s drain timeout.
- **Resolution Steps:**
  1. Increase stop timeout in `manifest.yml` or CLI:
     ```bash
     cf set-env <app_name> CF_STOP_TIMEOUT 60
     ```
  2. Implement proper `process.on('SIGTERM', ...)` handlers in Node.js to close HTTP listeners and database connection pools promptly.

#### D. Health Check Failures (Starting / Flapping)
- **Symptoms:** Application status remains `starting` until it fails and crashes.
- **Diagnostic Signature:** `cf events <app>` indicates `health check timed out`.
- **Root Cause:** App did not bind to the port defined in `$PORT` within `health-check-timeout` (default 60s), or HTTP endpoint returned non-200.
- **Resolution Steps:**
  1. Ensure application binds to `process.env.PORT` (or default `8080`) on `0.0.0.0`.
  2. For slow starting microservices, increase health check timeout:
     ```bash
     cf set-health-check <app_name> http --path /health --timeout 180
     ```
  3. Restart the application:
     ```bash
     cf restart <app_name>
     ```

### 2. Gorouter & Ingress HTTP Errors

#### A. 502 Bad Gateway
- **Symptoms:** Endpoints return HTTP 502.
- **Diagnostic Signature:** `TraceEvents` contains `component: 'RTR'`, `statusCode: 502`.
- **Root Cause:** Gorouter connected to container port, but the container abruptly reset the connection or crashed while handling the request.
- **Resolution Steps:**
  1. Correlate `RTR` timestamp with `APP` error logs:
     ```bash
     cf logs <app_name> --recent
     ```
  2. Inspect whether the container crashed mid-request (e.g. fatal segfault, out of memory).
  3. Verify reverse proxy headers and ensure keep-alive timeouts exceed Gorouter timeouts.

#### B. 503 Service Unavailable
- **Symptoms:** Route is reachable but returns HTTP 503.
- **Diagnostic Signature:** `statusCode: 503`, Gorouter header `X-Cf-RouterError: unknown_route` or `endpoint_failure`.
- **Root Cause:** No active app instances registered with the router for this route (e.g., all instances crashed or app is `STOPPED`).
- **Resolution Steps:**
  1. If application is stopped, start it:
     ```bash
     cf start <app_name>
     ```
  2. If instances crashed, scale to multiple instances for high availability:
     ```bash
     cf scale <app_name> -i 2
     ```
  3. Verify route mapping:
     ```bash
     cf routes
     cf map-route <app_name> <domain> --hostname <host>
     ```

#### C. 504 Gateway Timeout
- **Symptoms:** Slow operations fail after 60–120 seconds with HTTP 504.
- **Diagnostic Signature:** `statusCode: 504`, router `response_time >= 60.000`.
- **Root Cause:** Upstream microservice took longer to complete request than Gorouter timeout.
- **Resolution Steps:**
  1. Offload long-running synchronous calls to asynchronous background jobs (e.g., SAP Event Mesh, message queues).
  2. Optimize database queries, indices, and OData `$select` / `$filter` projections.
  3. Increase request timeout in application manifest if supported:
     ```yaml
     timeout: 180
     ```

### 3. Buildpack & Staging Errors

#### A. Staging Disk or Memory Quota Exceeded
- **Symptoms:** `cf push` fails during droplet creation.
- **Diagnostic Signature:** `staging failed: Insufficient resources` or npm compilation killed.
- **Root Cause:** Dependencies (`node_modules`, JARs) exceeded staging disk or memory quota.
- **Resolution Steps:**
  1. Exclude unnecessary assets using `.cfignore` (e.g., `test/`, `docs/`, `.git/`, local `node_modules`).
  2. Increase container disk limit:
     ```bash
     cf scale <app_name> -k 2G
     ```
  3. Supply staging memory allocation in `manifest.yml`:
     ```yaml
     staging_memory: 2048M
     ```

---

### 4. Authentication, Security & Account Errors

#### A. Account Locked (`PASSWORD_LOCKED`)
- **Symptoms:** `cf login` or token fetch returns `User account is locked`.
- **Root Cause:** Consecutive invalid password attempts on SAP BTP / SAP Cloud Identity Services (IAS).
- **Resolution Steps:**
  1. Unlock user account in SAP Cloud Identity Services Administration Console or SAP BTP Cockpit.
  2. In `default.env`, migrate authentication from user password to **Client Credentials** (`CF_CLIENT_ID` / `CF_CLIENT_SECRET`) or **Direct Bearer Token** (`CF_BEARER_TOKEN`).
  3. Locally, refresh active developer CLI session:
     ```bash
     cf login -a <api_url> --sso
     ```

#### B. 403 Forbidden / Insufficient Permissions
- **Symptoms:** `CF-NotAuthorized` when querying `/v3/apps` or managing routes.
- **Root Cause:** User or service key lacks required space role.
- **Resolution Steps:**
  1. Assign `SpaceDeveloper` role to the account:
     ```bash
     cf set-space-role <username> <org> <space> SpaceDeveloper
     ```

---

### 5. Backing Service Connectivity & Database Errors

#### A. SAP HANA Cloud Hibernated / Stopped
- **Symptoms:** App fails with `ECONNREFUSED` or `Cannot connect to HANA database`.
- **Diagnostic Signature:** `TraceEvents` logs error connecting to port `443` on HANA host.
- **Root Cause:** SAP HANA Cloud trial or dev instance entered automatic hibernation due to inactivity.
- **Resolution Steps:**
  1. Navigate to **SAP HANA Cloud Central** in the SAP BTP Cockpit.
  2. Locate the stopped HANA database instance and click **Start** / **Resume**.
  3. Once the database status turns **RUNNING**, restart the CAP service:
     ```bash
     cf restart <app_name>
     ```

#### B. Broken or Outdated Service Binding
- **Symptoms:** Authentication or destination service lookup fails with credentials rejection.
- **Resolution Steps:**
  1. Unbind and rebind service instance:
     ```bash
     cf unbind-service <app_name> <service_instance_name>
     cf bind-service <app_name> <service_instance_name>
     ```
  2. Restage the application to inject updated `VCAP_SERVICES`:
     ```bash
     cf restage <app_name>
     ```

## 🤖 Autonomous AI Agent Remediation Workflow (MCP Loop)

AI Agents consume this service through the **Model Context Protocol (MCP)** tools (`incidents_query`, `incidents_get`, `incidents_update`, `traceEvents_query`, `messages_create`).

### Standard 5-Step Autonomous Remediation Protocol:

```
┌────────────────────────┐      ┌────────────────────────┐      ┌────────────────────────┐
│ 1. Scan Incidents      │ ───► │ 2. Inspect Traces      │ ───► │ 3. Diagnose Root Cause │
│ (incidents_query)      │      │ (traceEvents_query)    │      │ (Match CF Catalog)     │
└────────────────────────┘      └────────────────────────┘      └────────────────────────┘
                                                                            │
┌────────────────────────┐      ┌────────────────────────┐                  │
│ 5. Audit Message Log   │ ◄─── │ 4. Write Remediation   │ ◄────────────────┘
│ (messages_create)      │      │ (incidents_update)     │
└────────────────────────┘      └────────────────────────┘
```

1. **Step 1 - Discover Active Incidents:**
   Query open or investigating incidents:
   - Tool: `incidents_query`
   - Filter: `status eq 'INVESTIGATING' or status eq 'OPEN'`
2. **Step 2 - Retrieve Telemetry & Traces:**
   Inspect underlying logs and exit codes for the incident:
   - Tool: `traceEvents_query`
   - Filter: `incident_ID eq '<incident_uuid>'`
3. **Step 3 - Synthesize Root Cause Statement:**
   Match trace data and status codes against the **Cloud Foundry Error Resolution Catalog** above.
4. **Step 4 - Update Incident with Remediation Action:**
   Post prescriptive resolution commands directly to the incident:
   - Tool: `incidents_update`
   - Parameters:
     - `ID`: `<incident_uuid>`
     - `status`: `'RESOLVED'` (if remediation executed) or `'INVESTIGATING'`
     - `errorCategory`: `'CF_APP_CRASH'` | `'CF_PROCESS_CRASH'` | `'CF_ROUTE_MUTATION'` | etc.
     - `rootCauseStatement`: Concise diagnostic statement (e.g., `Container killed due to Out Of Memory (Exit 137).`)
     - `remediationAction`: Concrete CLI commands (e.g., `Run 'cf scale <app> -m 1G && cf restage <app>'`)
5. **Step 5 - Log Diagnostic Comment:**
   Append a transparent execution message for SRE operators:
   - Tool: `messages_create`
   - Parameters:
     - `incident_ID`: `<incident_uuid>`
     - `text`: `Autonomous AI diagnosis completed. Identified OOM (Exit 137). Remediation action posted.`
